# 01 背景与目标

## 1. 背景

给客户做后台管理系统，是一个**重复度极高**的活：

- 每个客户都要：登录、菜单、用户、角色、字典、一堆「xxx 管理」页面
- 每个管理页面都是：搜索栏 + 表格 + 分页 + 新增/编辑弹窗 + 删除 + 操作按钮
- 真正跟业务相关的差异，往往只有「表名、字段、搜索条件、几个特殊按钮」

传统做法是每个客户复制一套代码改，结果是：**N 个客户 = N 套代码 = N 倍维护成本**。

## 2. 目标

把「重复的部分」抽成框架，让**做一个管理页面**从「写代码 + 发版」变成「在后台点几下」：

| 维度 | 传统做法 | 本系统 |
|---|---|---|
| 新增一张业务表页面 | 写 vue + 写接口 + 写 SQL + 发版 | 后台配字段 → 拿 TCID → 配路由 |
| 加一个字段 | 改表 + 改实体 + 改前端 + 发版 | 配置里加一行（`ADD COLUMN`） |
| 新增一个客户 | 复制代码 + 改配置 + 部署 | 新建子系统 + 分配给客户 |
| 改下拉选项 | 改代码发版 | 改字典 |

## 3. 角色

| 角色 | 是谁 | 能做什么 |
|---|---|---|
| **超管** | 平台方运营/开发 | 登录主系统；建子系统；切到任意子系统配路由/表格/用户/角色/字典 |
| **子系统管理员** | 客户方管理员 | 登录自己的子系统；管理本系统的用户、角色、路由、表格、字典 |
| **子系统普通用户** | 客户方员工 | 登录后只看到有权限的菜单，做业务数据的增删改查 |
| **前端开发者** | 平台/客户的技术人员 | 写自定义页面（`.vue`），用 `<Table :tcid>` + 插槽接管特殊逻辑 |

## 4. 目标（可验收）

1. 超管用 `yy1 / yy1129273677` 登录主系统
2. 新建一个子系统（如 `demo`），顶栏切过去
3. 配一张表格（字段、搜索、按钮），拿到 TCID
4. 建一条 TABLE 路由绑定该 TCID
5. 刷新页面 → 左侧出现菜单 → 点开就是可增删改查的页面
6. 写一个自定义页面（`.vue`），配 CUSTOM 路由，菜单出现，页面里的 `<Table>` 正常渲染，插槽生效

> 全流程不需要改后端代码、不需要新增接口。

## 5. 非目标

| 不做 | 原因 |
|---|---|
| 低代码「任意页面拖拽」 | 本系统只解决「列表页 + 表单」这类 CRUD 场景，不做通用低代码平台 |
| 开放原始 SQL 给配置者 | 注入风险；用结构化搜索 DSL 替代（见 ADR 0001） |
| 删除字段时同步删列 / 改列类型 | 会丢数据，必须人工执行 |
| 语义检索（embedding） | pgvector 已预埋，但不接模型；接模型涉及成本与效果评估 |
| 单点登录 / OAuth / 多因素 | 当前账号体系够用，属于后续扩展 |
| 前端包体优化 | 全量引入 Element Plus，优先开发效率 |

## 6. 约束（必须遵守的技术现实）

| 约束 | 影响 |
|---|---|
| 配置者会填表名/列名，而 SQL 里表名列名**无法参数化** | 必须有严格的标识符白名单校验（`identifiers.ts`），否则就是注入 |
| 一张 TCID = 一张物理表 | 表数量随配置增长；每张表结构独立，改类型要重写表 → 只允许加法 |
| 权限签在 token 里 | 权限变更是「下次登录生效」，不是实时的 |
| 子系统数据隔离靠 `system_id` | 任何查询漏掉它 = 跨租户泄露，属于最严重的 bug |
| 服务器一般 2~4G 内存 | 构建镜像时容易 OOM，部署文档里要求开 Swap |
| 客户常在内网 / 无域名 | 部署走 `IP:端口`，前端用 hash 路由避免 Nginx 回退配置 |
