# ADR 0001：技术栈与「TCID + 物理表」方案

- 状态：已采纳（Accepted）
- 日期：项目启动时
- 决策人：项目负责人
- 相关文档：`docs/design/02-domain.md`、`docs/design/06-failure.md`

---

## 背景

要做一个「配置驱动」的多租户后台框架：超管在后台配一张表，生成 TCID，前端 `<Table :tcid>` 一行渲染。
核心问题是三个：

1. 技术栈选什么（团队要能维护、上手快）
2. 「表格配置」和「真实数据」怎么存（这是全系统最关键的决策）
3. 「自定义搜索语句」怎么开放（安全 vs 灵活）

---

## 决策 1：技术栈

**采纳**：前端 Vue3 + Vite + Element Plus；后端 NestJS + Prisma + PostgreSQL 16；认证 JWT。

| 备选                                 | 优点                                                                                                             | 缺点                                                                         | 结论 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ---- |
| Spring Boot + MyBatis Plus           | 生态成熟、国内资料多                                                                                             | 前后端两套心智；动态 SQL 靠 XML 字符串拼（正好是本项目最危险的地方）；镜像重 | ❌   |
| Express/Koa + Sequelize              | 轻                                                                                                               | 没有约定，权限/守卫/模块分层全要自己造；动态表用 Sequelize 很别扭            | ❌   |
| **NestJS + Prisma**                  | 守卫/拦截器/依赖注入天然贴合「权限 + 统一响应」；Prisma 的 `$queryRaw` 标签模板做参数化动态 SQL 很顺手；类型贯通 | Prisma 对动态表支持有限（要绕开用 raw SQL）                                  | ✅   |
| React + Ant Design Pro               | 组件丰富                                                                                                         | 与团队已用的 Vue 栈不一致；上手成本高                                        | ❌   |
| 直接套 Vben/Jeecg 之类的低代码脚手架 | 开箱即用                                                                                                         | 体积巨大、理解成本高、改一处牵全身；本需求只要 20% 的功能                    | ❌   |

**代价**：

- Node 服务内存占用比 Java 低，但构建镜像时内存峰值高（部署文档要求 2G+ / 开 Swap）
- Prisma 不方便做动态 DDL，需要 `$executeRawUnsafe`（已用白名单把风险关住）

---

## 决策 2：TCID + 每张表一张物理表（vs 单表 JSONB / EAV）

**采纳**：一个 TCID → 一张真实表 `biz_<tcid>`，字段即列（`ADD COLUMN` 加字段）。

需求原文是「**表格字段即为数据库字段**」，这句话就是决策依据。

| 备选                                       | 优点                                                                          | 缺点                                                                           | 结论                           |
| ------------------------------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------ |
| **每表一张物理表 + TCID**                  | 完全符合需求；能直接用 SQL 查报表；性能好（有真实列类型）；数据迁移到别处容易 | DDL 有风险（已用白名单 + 只做加法兜住）；表数量随配置增长；Prisma 无法静态建模 | ✅                             |
| 单表 + JSONB（`record(tcid, data jsonb)`） | 零 DDL、极灵活、加字段免费                                                    | 不符合"字段即数据库字段"；查询要靠 GIN 索引，复杂条件慢；类型无约束；报表难写  | ❌（但留作小数据量场景的备选） |
| EAV（`entity/attr/value` 三表）            | 灵活                                                                          | 查询要多次 JOIN，性能差，SQL 可读性极差                                        | ❌                             |
| 每配一张表就生成 Prisma model + 跑 codegen | 类型安全                                                                      | 需要重新编译/重启，运行时不可行                                                | ❌                             |

**后果**：

1. **DDL 只能做加法**：`CREATE TABLE` / `ADD COLUMN`。删列、改类型必须人工（见 `06-failure.md`）
2. **表名/列名进 SQL 文本**（PostgreSQL 不支持参数化标识符）→ 必须有严格白名单校验
3. **业务字段不自动建索引** → 数据量大时人工加
4. 表数量会增长（一个客户 10 张表、100 个客户就是 1000 张），PostgreSQL 能承受，但要监控

**什么情况下会改推另一个方案**：

- 如果客户表都是"几万行、几十个字段、极多定制"→ 仍用物理表
- 如果是"海量小表、字段经常变、几乎不写复杂查询"→ 改 JSONB 单表更划算

## 决策 3：搜索用结构化 DSL，不开放原始 SQL

**采纳**：`{"mode":"CUSTOM","group":{logic, not, conditions[], groups[]}}`，后端校验后生成参数化 SQL。

| 备选                                                     | 优点                                                                                 | 缺点                                                             | 结论          |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------- | ------------- |
| **结构化条件组**                                         | 表达能力与 WHERE 等价（AND/OR/NOT 任意嵌套）；值全参数化；字段白名单；可校验、可测试 | 配置者需要理解一点 JSON 结构；复杂场景下不如手写 SQL 直观        | ✅            |
| 允许填原始 WHERE 字符串                                  | 最灵活                                                                               | **SQL 注入面直接交给超管**；慢查询无法拦；字段名拼错运行时才炸   | ❌            |
| 引入 SQL 解析器（如 pgsql-ast-parser）做语法校验后再执行 | 灵活 + 相对安全                                                                      | 依赖体积大、解析器有边界；校验失败时的错误提示对非技术人员不友好 | 🤔 需要时可上 |

**后果**：

- 需求里"自定义语句"以「结构化自定义」形式满足；如果确实需要原始 SQL，需要额外加「超管高级模式 + 审计日志 + 只读账号执行」，这是另一个量级的工程
- 搜索的字段/运算符被严格限制，配置错误会得到明确的中文 400，而不是数据库报错

## 决策 4：权限快照在 JWT 里

**采纳**：登录时把 `permissions` 签进 token，请求不查库。

| 备选                  | 优点               | 缺点                                   |
| --------------------- | ------------------ | -------------------------------------- |
| **权限快照**          | 零额外查询，吞吐高 | 权限变更需重新登录才生效               |
| 每次请求查库          | 实时               | 每个请求 +1 次查询，还要连角色表       |
| Redis 存权限 + 版本号 | 实时且快           | 多一个依赖（当前部署只有 PG 一个存储） |

**结论**：当前用量和变更频率下，快照更划算。文档里明确写"改权限需重新登录"。
如果业务要求实时，改成守卫查库（`sys_user` join `sys_role`），代价可接受。

## 决策 5：迁移离线生成 + 容器启动时 deploy；seed 手动

**采纳**：

- 开发：`prisma migrate diff --from-empty --to-schema-datamodel` 离线生成 SQL（不需要连库）
- 部署：容器启动命令里 `prisma migrate deploy`（幂等）
- 种子：**手动** `docker compose exec server npm run seed`，不放在启动命令里

| 备选                 | 问题                                                                |
| -------------------- | ------------------------------------------------------------------- |
| `prisma migrate dev` | 会连库、可能提示重置数据库；在没有数据库的环境（CI/新机器）直接失败 |
| 启动时自动 seed      | 每次重启都会动数据；seed 里有 upsert 也容易掩盖问题                 |

**后果**：新机器部署必须记得跑一次 seed，否则没有超管账号。
`DEPLOY.md` 里把这一步单独列成第 4 节，`update.sh` 不管它。

## 决策 6：前端 hash 路由 + Element Plus 全量引入

| 决策                  | 理由                                                          | 代价                        |
| --------------------- | ------------------------------------------------------------- | --------------------------- |
| hash 路由（`#/`）     | 部署到 Nginx 不需要 `try_files` 回退，少一个上线必踩的 404 坑 | URL 不好看                  |
| Element Plus 全量引入 | 组件用得多，全量最省事，图标也能动态渲染                      | 首屏 1.27MB（gzip 411KB）   |
| 页面级懒加载          | 业务页面按需加载                                              | 已做（`() => import(...)`） |

**什么时候改**：如果首屏性能成为指标，改成 `unplugin-vue-components` 按需引入 + 分包。

---

## 决策 7：文档结构 = 3 份运维 md + docs 骨架

**采纳**：

- 根 `DEPLOY.md`（部署/更新/备份/坑）
- `client/README.md`、`server/README.md`（各自的"做了什么 / 启动 / 注意"）
- `docs/`（术语表、领域模型、流程、状态、规则、失败模式、ADR）+ `AGENTS.md`（给 AI/接手者的约定）

**理由**：人和 AI 都要能快速定位。运维文档和设计文档混在一起，会两头都不好用。
`AGENTS.md` 的存在是为了让 AI 协作者知道"哪些绝对不能动"（比如标识符校验、DDL 只做加法）。

## 复查触发条件（什么时候该回来看这份 ADR）

- [ ] 业务要求「改字段类型」或「删字段」→ 决策 2 要重审
- [ ] 出现性能问题（搜索慢）→ 决策 2/3 要评估索引或换 JSONB
- [ ] 要求「权限实时生效」→ 决策 4 要重审
- [ ] 要求「配置者写原始 SQL」→ 决策 3 要重审（且需要安全方案）
- [ ] 首屏性能成为指标 → 决策 6 要重审
- [ ] 要接 embedding 做语义检索 → 在 `sys_vector_document` 上推进，不需要改现有表
